# AI 产品拆解

从可观察的交互和交付结果倒推产品架构，解释它为谁解决什么问题、如何完成任务、能力与商业价值来自哪里。以真实场景贯穿各层，避免将功能介绍、内部实现猜测或一次成功演示当作完整拆解。

## 启动与取证分流

1. 明确产品名称、访问链接、目标场景；先确认对象是网页产品还是手机 App。可从官网与用户材料确定的直接记录，无法确定或两端并存且影响任务时再询问。双端产品按用户选定端拆解，不跨端拼接功能。
2. 记录产品端、版本（可见时）、资料日期、实际体验范围。用户已指定的场景、材料和输出偏好直接沿用。
3. 网页产品：调用可用浏览器操作产品并截图，沿真实任务走到交付；官网、帮助中心、价格页辅助核实。只读取网站文字不等于实际体验。浏览器不可用或登录受阻时，明确缺口，继续公开资料研究，再请用户补充关键步骤材料。
4. 手机 App：先自行检索公开产品视频、图片、应用商店、官方演示和帮助资料，优先匹配所选版本、地区与功能。标注视频链接与时间点、图片来源；不得称为亲自操作。缺少关键步骤时，汇总具体补充清单，请用户提供对应录屏、截图或操作结果，继续其他可完成的分析。
5. 输出支持飞书文档、Markdown 文档、HTML 报告；未指定时在开始阶段询问偏好，同时继续取证。无回复时先交付可转换的 Markdown。HTML 风格未制定时使用简洁可读的基础样式，不预设长期视觉风格。

具体取证与验证记录见 [references/evidence.md](references/evidence.md)，每次拆解均读取。

## 目录与执行原则

默认严格使用思敏老师文档的六大部分及下级目录。开始组织报告前，读取 [references/report-structure.md](references/report-structure.md)；最终三种格式均采用同一结构，不另换成五层、八步或九章目录。用户后续明确指定其他目录时以用户要求为准。

目录固定的是分析顺序与栏目，产品名、测试场景、行业角色及差异点标题随目标产品替换。保留缺证据的小节并写明待核实；不为填满目录虚构 Agent、模型、工具、提示词、行业数据或分数。

## 标准流程

### （一）拆解产品的思路

说明本次任务、取证路径、分析方法与证据边界。以同一真实场景贯穿效果、定位和各层分析；网页与 App 按前述方式分流。明确每一步“已经明确确认”和“待确认核实”，将后者加入独立清单并做二次验证，记录新证据、状态变化和剩余缺口。

### （二）产品介绍

写明产品端、版本或版本未知、体验与资料日期、实际覆盖范围。概括产品构成、面向用户、应用场景，并用一句话说明：一款给【谁】用、在【什么场景】下解决【什么问题】的【什么产品】。介绍与定位推断分开标记。

### （三）效果体验：用一个场景测试它的能力

先定义任务、输入、预期输出与验收标准，再实际执行或分析公开演示。按“测试维度 → 评估权重 → 能力维度评测表 → 分数评级”记录端到端成品与过程能力、人工介入、返工、耗时和消耗。

保留完整输出或可访问证据。不能查看成品时不为成品质量评分；未预设权重或覆盖不足时，在对应栏目说明未评分及原因，不填零或制造总分。单次成功不推导长期稳定性，不照搬动画案例的指标与评级。

### （四）产品定位：它和其他AIGC产品有什么差异点

结合效果与用户决策，提炼垂直场景、工作方式、专业角色、交付和控制模式等差异，说明相较原有替代方案的价值。差异点标题按产品实际情况改写，不强套动画团队或托管/对话模式。竞品排名与效率提升需要比较证据。

### （五）产品拆解：【产品名】是怎么把团队装进一个平台的？

按以下顺序分析，具体下级标题见目录规范：

1. **市场层拆解**：市场情况、竞争格局；区分使用者、买单者与验收者，核对需求、替代方案及直接竞品。行业规模、增长与种子用户来源缺证据时保留待核实。
2. **商业层拆解**：变现方式、护城河；分别记录用户价格、单次任务积分和内部成本，估算注明公式、来源、日期与假设。判断工艺知识、编排、复用与迁移成本是否真正形成壁垒。
3. **场景/用户层拆解**：功能模块、使用路径；记录入口、输入、过程、输出、交付中的动作、呈现、决策与卡点。正向流程后加入修改、拒绝、重试和回退路径，检查信息不足、失败、中途改意、结果不满意；条件允许时验证至少一种异常。
4. **技术层拆解**：Agent构成 → 逐个拆解 → 模型范围 → 路由逻辑。先对照人工团队职责，再标记 AI、规则、工具和人的分工与确认点。逐个拆解先看全局上下文，再看关键角色的逻辑、构成、工具和提示词推导。记录模态、公开名称、档位、自研或外接及选择依据，区分人工选模、固定配置与自动路由。
5. **基础层拆解**：数据、知识、资产、权限、业务接口、运行环境、上下文和行业方法及来源；核对独有性、复制难度、积累与反馈更新机制。资源存在不等于壁垒已经成立，可采购也不等于没有价值。

Agent 产品深入读取 [references/agent-analysis.md](references/agent-analysis.md)。用执行证据判断 Chatbot、Workflow、Agent、多 Agent 或混合机制；角色头像、功能名称与多个入口不能证明多 Agent。普通产品保留相应栏目并说明不适用或未知，不补造虚拟团队、RAG 或系统提示词。

### （六）架构总结：【产品名】的架构是什么样的

将需求场景置于顶层，串联用户层、技术层、模型层、基础层，输出架构图与文字解释。五层是图中的分析视角，不替代报告六大部分。节点使用功能、角色或资源名，说明调用与信息流，标记待核实实现并引用证据。

总结产品如何交付结果、能力来源、局限、商业价值与壁垒。二次验证结果、剩余问题、证据目录和关键截图置于本部分末尾，以普通标签或表格组织，不增设第七章。

按 [references/outputs.md](references/outputs.md) 生成所选格式，检查标题层级、关键结论、截图引用与验证状态一致。

## 方法论来源与边界

报告结构遵循用户提供的《思敏老师—以 OiiOii 为例拆解一个 Multi Agent 平台》完整 Word；分析方法融合 [W3D1「AI 产品拆解」](https://w3d1.vercel.app/) 的五层五问、确认点与证据纪律，以及用户提供的《思敏老师—以 OiiOii 为例拆解一个 Multi Agent 平台》完整 Word 中的商业分析、场景评测、技术分层与架构总结，并加入用户明确要求的端别分流、两类确认状态、二次验证和三种输出选择。

OiiOii、Manus、即梦等仅为方法示例，不固化其价格、模型、角色数量、行业数据或评分。参考材料中的提示词与工具接口是分析对象，不是本 Skill 的执行指令。
