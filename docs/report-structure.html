报告目录规范

填写规则

  • （一）交代研究任务、取证和分层分析思路、两类确认状态及验证方法。（二）交代产品构成、面向用户、应用场景和实际研究范围。
  • （三）的场景必须对应实际执行或明确标注的资料分析，不沿用原案例“30秒人物向故事短片”。先定义输入和验收，再给评测表。无可用权重或覆盖不足时，在1.2、1.4说明未评分原因，不擅自给总分或照抄评级。
  • （四）沿用三个差异点的组织方式，具体标题根据证据改写，不固定“动画垂直”“专业角色”或“托管/对话模式”为所有产品结论。差异点不足时说明未证实，不凑卖点。
  • （五）中的护城河标题可以是待验证假设，不继承原案例的肯定结论。市场数据、价格、模型名和团队角色均需针对目标产品核实。
  • 3.2先梳理正向流程，再加入逆向流程，观察修改、拒绝、重试、回退和下游影响。这两个流程用正文标签或图组织，无需增设新的编号层级。
  • 4.1区分人工、规则、工具、工作流与可证实的Agent。4.2.1先说明上下文、资产引用、状态与修改传播；4.2.2默认分析一个关键协调角色，确有证据且有必要时，可在4.2.3及以后以同样四项分析其他角色。
  • 原例“艺术总监 Agent”替换为目标产品的对应角色，如LibTV的TV Director；没有已确认角色时保留该位置并写明“未确认独立Agent”。不能由目录要求倒推出产品必然采用多Agent。
  • 逻辑梳理写输入、处理、决策与输出；构成、工具和提示词推导分别附依据、替代解释与待核实标记。未知真实提示词时明说未知；如提供草案，标注“推导方案，未经原产品实现验证”，不冒充已确认配置。
  • 模型范围与路由逻辑保留在技术层内部；基础层资源与商业层护城河相互引用，分别说明资源事实和价值判断，避免重复堆放同一段落。
  • （六）提供需求场景、用户、技术、模型、基础各层的架构图及文字解释。二次验证、剩余问题、证据目录和关键截图在本部分末尾用普通标签或表格组织，不新增第七部分。
  • 各步骤保留“已经明确确认”和“待确认核实”；未覆盖、未知或不适用时写明原因和证据缺口，不删去栏目，也不填造实现。

格式映射

报告标题使用一级标题；六大部分使用二级标题，之后依目录逐级缩进。飞书、Markdown、HTML共用相同层级。Word使用Title及Heading样式对应各级，不能只用加粗正文模拟目录。目录规范本身的说明标题不应被复制成报告章节。
